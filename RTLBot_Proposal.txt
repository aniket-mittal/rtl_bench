Overview of the Project
We propose TrainRTL, a system for training open weight LLM agents to repair, implement, and optimize RTL hardware designs using rewards obtained from EDA tools. Each agent works in an isolated RTL workspace, submits code changes, and receives independently verified feedback from compilation, simulation, hidden functional tests, and synthesis. [a]
We plan to use AWS Trainium2 to run and train the LLM, while CPU workers will use hardware tools to check whether the RTL generated by the agent is correct and measure its area and timing. We will study how to efficiently connect these hardware evaluations to the RL training process, especially when agents take different amounts of time to complete tasks. Our deliverables will include a collection of RTL tasks, an open source training environment, code for connecting the environment to RL training frameworks, saved model checkpoints when permitted, and a technical report documenting our experiments and results.
Introduction
LLMs can generate RTL that compiles but fails on edge cases, or that works but wastes area and timing. Benchmarks have progressed from single turn generation (VerilogEval [1]) to agentic, tool using tasks such as debugging and design improvement (CVDP [2]). RL with EDA derived rewards has improved correctness (CodeV-R1 [3]) and PPA (ChipSeek [4]), but these methods train models to generate designs from a spec in a single response. ChipMATE [5] trains multi-turn agents, but for writing new designs rather than modifying existing ones.
TrainRTL improves on this work in three ways:
1. Agentic repair and optimization. We train agents with RL to repair and optimize existing RTL in a tool using workspace where they can compile and run public tests before submitting.
2. Stronger verification. Prior rewards rely mainly on testbench simulation, which can reward incorrect designs or “optimizations” that just delete untested logic. We use hidden tests and formal equivalence checking, and can measure how much weaker verifiers inflate results.
3. Efficient training on Trainium2. EDA evaluation is slow and variable. We study how to schedule it alongside RL training on Trainium2 to minimize idle time and cost per solved task.
Methods
1. Task contract
Our main focus will be on fixing bugs and improving the efficiency of existing RTL designs, starting with smaller hardware components such as FIFOs, arbiters, counters, pipelined arithmetic units, and memory interfaces. We will also explore tasks where the agent generates RTL from a written specification, provided that we have a reliable reference design to verify correctness. We will prioritize tasks that have a larger solution space, to allow the agent to explore different implementations and learn how to balance area, timing, and functionality.
Each task will include:
1. A written spec of what the hardware should do and its interfaces
2. Any starter RTL code and a list of files the agent can modify
3. Available tools and runtime limits
4. Public tests the agent can run
5. Hidden tests, reference implementations, or formal checks to independently verify correctness
2. Task generation
We plan to create a separate task generator that will create debugging tasks from open source RTL by injecting bugs or removing parts of existing designs. This way each task will have a correct reference implementation and include tests that detect the introduced bugs. We will also use formal verification where possible.
We plan to start with 10 - 30 tasks to test the framework, then expand to approximately 120 tasks. Tasks will be split into training, development, and test sets using different codebases to reduce overlap.
3. RL environment
Each agent will work in an isolated container with access only to its assigned task, public tests, and approved tools. A separate container will evaluate the submitted RTL using hidden tests and synthesis to check correctness, area, and timing. The agent cannot access or modify the hidden tests or grading tools. We will also enforce time and compute limits to ensure reliable results.
4. Baselines and measurement
To validate the efficacy of our system, we will benchmark:
1. The base model with no training
2. The same model trained with correctness only tasks with RL
3. The same model trained with correctness + synthesis performance tasks with RL
Correctness metrics: hidden test pass rate, compilation success 
Performance metrics: synthesized cell area, critical path delay, and per task tool time
We will experiment with the weightage of these metrics in the RL reward function design to see what works best.
5. Agent/environment design
The system will run one shared LLM alongside multiple CPU workers that evaluate hardware tasks in parallel. A central coordinator will manage agent interactions, collect training data, and schedule tool execution so agents do not waste time waiting for synthesis. We will use Amazon S3 to store tasks, results, and model checkpoints.

6. RL Training
We will use Group Relative Policy Optimization (GRPO) to train the LLM. For each task, the model will generate eight independent attempts, which will be evaluated and compared to determine how to update its weights. Rewards will prioritize functional correctness, with additional rewards for area and timing improvements only when the design is fully correct. We will also limit the number of steps per attempt and save model checkpoints throughout training.
7. Trainium2 implementation
We will use AWS Neuron and PyTorch/TorchNeuron to train our LLM on Trainium2, with the initial plan to build on existing Qwen3-8B examples[b][c][d]. Before running any full experiments, we will verify that the model can generate responses, update its weights through RL, and save and reload checkpoints.

	Success criteria and dissemination
We aim to achieve an RL training system on Trainium2 with (1) at least a 10 percentage point improvement in correctness on unseen tasks compared to the untrained model, using the same inference budget, and (2) reduce hardware area and delay by at least 5% compared to a model trained only for correctness. We will also document any challenges or unsuccessful experiments.
Novel Hardware Exploration
We will study how efficiently AWS Trainium2 can train and run LLM agents while CPU workers evaluate their RTL designs. Since agents take different amounts of time to complete tasks, we will investigate how to minimize idle time and improve overall performance. We will measure (i) model training and inference speed, (ii) Trainium utilization, (iii) time spent waiting for hardware verification, and (iv) compute cost per successfully completed task.
We will also use Neuron profiling tools to identify performance bottlenecks. If needed, we may use the Neuron Kernel Interface (NKI) to optimize specific operations and measure their performance improvements [6–8].
Open-Source Integration
TrainRTL will use PyTorch/TorchNeuron and AWS Neuron to train the LLM, along with open-source hardware tools such as Verilator and Yosys for RTL verification and synthesis[e]. We will also use the open source NeMo gym for harness infrastructure. The framework, task dataset, training scripts, and experimental results will be developed for internal use by Annapurna Labs. We will not publicly release project code, datasets, or proprietary information.

	Risks, Reproducibility, and Responsible Research
The main risks are unreliable tests, limited RL training feedback, Trainium compatibility issues, and slow hardware verification. To address these, we will (1) validate tasks against correct reference designs, (2) use supervised fine-tuning if RL training is unsuccessful, (3) test Trainium compatibility early, and (4) run hardware evaluations in parallel. Final results will be measured using hidden tests and synthesis metrics on functionally correct designs. We will only use public or authorized RTL and comply with commercial tool licensing restrictions.
